# 每日记录 - 2026-09-10

> 主题：Agent 产品认知与 vlm-agent 数据闭环。
> 今日收敛：以真实项目和现有技术为主线，按需补基础，不深入 VLM 预训练全栈，也不把讨论变成技术答辩。

## 一、学习范围：把项目闭环弄明白

**目标：理解数据如何改善模型能力，以及这种改善如何转化为 Agent 的任务完成效果。**

- **业务流程：** 能力诊断、数据准备、训练、评测、失败归因与再次补充。
- **工程流程：** 数据从哪里来，如何入库、去重、构造、审核并交付。
- **必要算法基础：** 视频输入与抽帧、Rollout 与 SFT、loss 与监督目标、数据配比、过拟合与遗忘。理解其作用即可，暂不展开架构推导与分布式预训练。
- **应用讨论：** 从用户当下办不好的具体任务出发，用成熟的检索、规则、API 和模型能力改善体验，不预设全自主或多 Agent 架构。

后续以“一条真实视频样本从采集到评测反馈”为线索，遇到必要概念再解释。

## 二、Agent 产品：从回答问题到完成任务

**我的观察：** 传统业务中台提供基础能力，Agent 可以作为新的 AI 入口，通过 MCP、CLI 等连接多个系统；AI-native 产品则围绕 AI 交互组织核心体验。交付从短答案扩展到长任务，用户通过补充信息、调整目标和确认动作参与过程。

讨论后保留的几个判断：

- **AI-native 与自主性是两回事。** 前者描述核心体验，后者描述系统可以自行执行哪些动作。LangChain、LangGraph 是开发框架，Harness 是运行支撑，不应与产品形态混为一层。
- **变化不只是输入输出，而是有限授权下的任务委托。** 用户定目标与边界，系统承担更多过程决策；任务需要状态、产物、暂停和接管能力，不能只靠聊天记录。
- **参与多不等于体验好。** 创作讨论本身可能有价值，重复办事则更看重减少监督与返工。质量和安全达标后，再比较人工耗时。
- **VLM 能力与执行系统配合。** 在本项目中，视觉理解是 Agent 的子能力；运行系统提供工具、上下文、权限、反馈与验证。VLM 也可能承担规划，并非只能感知；框架也不能自动补齐模型短板。

**值得验证的应用切口：** 企业问答从返回制度走向材料准备，购物推荐从泛泛介绍走向具体候选对比，故障排查从通用建议走向基于日志的下一步检查。共同缺口是具体上下文、可靠数据和后续动作，尚不能认定为市场空白。

关于后台 Agent、A2A、长期记忆、结果计费等，暂保留为趋势假设，不认定“所有系统都会面向 Agent 重构”。

## 三、vlm-agent：数据如何变成能力

据现有项目文档，本轮是 **行为引导 Rollout + 靶向 SFT**，不是从零预训练，也不是 RL 参数更新。

```text
Agent 任务失败 -> 定位视觉理解缺口 -> 定义能力与难度
-> 靶向视频数据构造与质检 -> Rollout 筛选正样本 -> SFT
-> 目标能力 / 未见任务 / 通用回归 / Agent 端到端评测
-> 归因剩余问题 -> 下一轮数据或系统改进
```

**数据 Pipeline：** 考点驱动的 YouTube/B 站视频寻源 -> TOS 入库与元数据登记 -> 视频去重 -> 生成问题、CoT 与答案候选 -> 作业表 -> 人工终审与交付。生成候选不等于合格训练样本，下游筛选和实际消费需与算法侧核实。

**发现边界的方法：** 固定模型和基本推理配置，逐步改变视频长度、证据间隔、干扰或跨片段推理要求，观察分项表现与失败类型。能力边界取决于输入与预算，不由一道错题决定。

| 发现的问题 | 优先动作 |
|------------|----------|
| 关键动作未进入抽帧输入 | 修抽帧、片段检索或输入预算 |
| 证据可见，但特定关系反复判错 | 补该能力的新样本，小批训练验证 |
| 开发集上涨，未见题不涨 | 查重复、泄漏、过拟合与覆盖不足 |
| 视觉能力提高，任务仍失败 | 查规划、工具参数、状态反馈与恢复 |
| 结果正确但 Judge 判错 | 先修评测，再解释模型效果 |

**高质量数据可以改善理解与推理，但不是保证。** SFT 通过目标输出的预测误差更新参数；数据要正确、命中缺口、有有效证据与多样性，并被合适的训练方式消费。训练 loss 下降不等于泛化，持续用于诊断的集合属于开发资源，需另留独立样本验收。

**“VLM scaling 失败”仍是疑问。** 需要明确扩展的是参数、数据、视觉 token 还是推理预算，以及在哪种分布和指标上失效。局部收益递减不能推出整体路线失败，靶向高质量数据与规模扩展也不对立。

**项目证据边界：** 文档记录内部 161 题中靶向覆盖 72 题、覆盖子集 +2.8，公开 ClawEval +0.5、WildClawBench +2.3；三套集独立，内部全量变化待确认。共享基座还有并行数据线，Agent 涨分不能全部归因于本项目，净贡献需消融验证。

## 四、数据质检：人定标准，Agent 执行与提疑点

**我提出的流程：** 人工制定初步 rubric -> 试标发现问题并修订 -> 标准趋稳后交给 Agent 自动质检 -> Agent 标识新疑点 -> 人工审核新标准、仲裁模型分歧。

需要补上的边界：

1. **标准稳定不等于 Judge 可靠。** “没有新问题”可能只是样本同质；应独立验收，并按能力维度和风险逐步开放自动化。
2. **既看分歧，也抽查一致。** 多模型可能一起错，一致通过和一致拒绝都需抽检。定向复核发现的问题率不能直接外推全量。
3. **先归因，再改 rubric。** 分歧可能来自证据不一致、标准含糊、模型执行错误或材料不足；证据不足允许待复核，不强行投票。
4. **标准更新与生产执行分开。** Agent 可以提议规则，人工批准并回归验证后发布；保留 rubric、模型和 prompt 版本，人工仲裁也要依据原始证据。

**错放与错杀的代价：**

| 错误 | 风险与限定 |
|------|------------|
| 错放坏样本 | 可能引入错误知识、推理或行为监督；总体指标未必暴露具体业务风险。最终答案正确也不能抵消被监督的错误 CoT |
| 错杀高价值样本 | 可能损失稀缺知识、解法或场景覆盖，**不必然导致难度降低**；高价值不等于高难度 |

单条样本不决定模型必然学错或不会，影响取决于替代数据、训练暴露与错误是否系统性集中。编造视觉证据不直接证明推理逻辑或视觉编码器出错；额外 token 和耗时也需实测。若错标进入的是 evalset，首先污染的是评测与决策，而非模型参数。
