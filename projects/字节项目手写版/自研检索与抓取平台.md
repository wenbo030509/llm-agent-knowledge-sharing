# 项目名称：自研检索与抓取平台（数据获取基建）

## 一、平台定位

面向 VLM 训练数据生产的**底层能力平台**，为上层的视频获取 Pipeline 与数据构造 Pipeline 提供统一的「搜得到、抓得下、存得住」能力。

平台本身**不绑定某个具体数据需求**（不关心这次要化学实验还是别的类型），只提供通用的检索、抓取、转存能力；具体“搜什么、留什么”的业务规则由上层 Pipeline 编排。

```text
上层业务（获取 Pipeline / 构造 Pipeline）
        │  调用能力
        ▼
┌─────────────────────────────────────────┐
│            自研检索与抓取平台（基建）      │
│  ┌────────────────┐   ┌────────────────┐ │
│  │   检索平台      │   │   Fetch 平台    │ │
│  │  Search         │   │  Fetch          │ │
│  │  关键词并发召回  │   │  解析/下载/转存  │ │
│  └────────────────┘   └────────────────┘ │
└─────────────────────────────────────────┘
```

两个子平台的边界：

- **检索平台**：输入检索词，输出候选视频 URL 与 Metadata。解决“视频在哪”。
- **Fetch 平台**：输入可用 URL，输出本地视频与 TOS 链接。解决“视频怎么拿到、存到哪”。

## 二、检索平台（Search）

### 2.1 能力

将“一批检索词”并发地打到视频源，召回候选视频，并把结果标准化为统一的候选记录。

```text
检索词集合（Query Set）
        ↓
    并发检索
        ↓
候选视频 URL + Metadata
```

返回的候选记录至少包含：

```text
video_url      候选视频地址
title          标题
author         作者 / 上传者
source         来源平台
duration       时长
publish_time   发布时间
query          命中的检索词（便于回溯哪条 Query 召回质量高）
```

### 2.2 两种检索入口

平台支持两类检索词来源，二者都走同一套并发召回：

```text
① 通用类检索（Rule-based）
   由人工按目标类型给定关键词（如：化学、生物、物理、实验操作），
   平台并发检索并返回 URL 及相关信息。

② 拓展类检索（Agent-based / auto-research）
   由 Agent 读取目标数据规则（Data Rubric），自主扩展长尾关键词，
   再执行并发检索（或接入检索平台接口），返回 URL 及相关信息。
```

设计意义：`通用类检索` 保证覆盖到高频、确定的目标类型；`拓展类检索` 通过 Query Expansion 扩大长尾场景覆盖，弥补人工关键词的盲区。两路召回合并去重后形成候选池。

> 平台职责边界：检索平台只负责“按词召回 + 标准化返回”，**不做内容筛选**。是否符合目标类型（标题规则、画质、内容质检）由上层获取 Pipeline 判定。

## 三、Fetch 平台（抓取与转存）

### 3.1 能力

将上层筛选出的**可用 URL** 转成可访问的视频资产，为下游标注与训练提供统一入口。

```text
可用 URL
    ↓
解析真实媒体流（yt-dlp）
    ↓
下载视频到本地
    ↓
转码 / 格式标准化（FFmpeg）
    ↓
转存对象存储，返回 TOS 链接
```

### 3.2 URL 解析

页面 URL 往往不是真正的媒体地址，需要先解析出可下载的媒体流。以 Bilibili 为例：

```text
页面 URL
    ↓
yt-dlp 解析
    ↓
真实媒体流入口（DASH / FLV 等 Format）
```

这一步同时暴露了媒体流的 Format 信息（分辨率、编码、时长等），上层的 Metadata / 画质预筛也依赖它。

### 3.3 并发抓取与状态管理

平台把每条可用 URL 转成一个异步抓取任务，用任务队列 + Worker Pool 并发执行：

```text
可用 URL
    ↓
Task Queue
    ↓
Worker Pool（并发 Fetch）
    ↓
本地视频
```

每条任务维护状态，实时回写：

```text
PENDING → RUNNING → SUCCESS / FAILED
                        ↓
                      RETRY → SUCCESS / FINAL_FAILED
```

### 3.4 失败重试

针对网络超时、CDN 异常、源不可用、下载中断等，设置重试机制并记录失败原因：

```text
error_code      失败类型
error_message   失败详情
retry_count     已重试次数
```

便于统计各来源失败率、定位问题 Source。

### 3.5 转码与 TOS 转存

下载后的视频统一转码标准化，再写入对象存储（TOS），返回可访问链接：

```text
本地视频
    ↓
FFmpeg 转码 / 格式标准化
    ↓
写入 TOS
    ↓
返回 TOS 链接（+ 回写转存状态：成功 / 失败，含失败重试）
```

TOS 链接是下游标注作业与训练的统一视频访问入口——上层拿到的不是易失效的原始页面 URL，而是持久、可控的 TOS 地址。

## 四、平台如何被上层复用

```text
[获取 Pipeline]
   检索平台  ← 通用/拓展两路并发召回候选
   Fetch 平台 ← 对筛选后的合格 URL 并发抓取 + 转 TOS
        │
        ▼  交付带 TOS 的合格视频
[构造 Pipeline]
   直接消费 TOS 视频做 Caption / QA / CoT 合成
   （不再关心视频怎么检索、怎么抓取）
```

一句话：**基建提供原子能力，获取 Pipeline 负责编排与质量判定，构造 Pipeline 只消费结果。**

---

## 五、设计要点

```text
1. 检索与抓取分离
   检索只召回 URL、抓取只处理可用 URL，中间由上层做筛选，
   避免把不合格视频也抓下来，减少带宽 / 存储 / 时间损耗。

2. 能力与业务解耦
   平台不写死“搜什么、留什么”，业务规则（关键词、Rubric、
   筛选标准）由上层传入，平台保持通用、可复用。

3. 并发 + 状态管理 + 失败重试
   检索并发召回、抓取并发执行，任务状态实时回写，
   失败可重试、可定位，保证大批量数据生产的稳定性。

4. TOS 作为统一交付入口
   下游拿到的是持久可控的 TOS 链接，而非易失效的页面 URL。
```
