# 项目名称：面向长视频复杂推理的证据检索式数据合成 Pipeline

## 项目背景

当前复杂视频推理任务面临高质量训练数据不足的问题。现有数据通常缺少两类关键内容：

- 必须依赖视频细节、经过多步推理才能回答的高难度问题；
- 能够体现“主动检索证据后再推理”的 video-grounded CoT。

这导致模型难以通过 SFT 和 RLVR 训练建立可靠的长视频理解、证据检索与复杂推理能力。

## 项目动作

### 1. 检索

与长视频复杂推理项目不同，本项目的视频获取以各类型已有的视频样例为基础，属于“根据视频检索视频”的同类型扩展任务，要求检索结果与样例视频的类型高度一致。

整体检索链路为：

**Caption → 关键词 → URL → 抽帧筛选 → 可用 URL**

其中，基于样例视频 Caption 提取和扩展检索关键词，召回候选视频 URL；再通过抽帧判断候选视频是否符合目标类型，最终筛选出可用 URL。

### 2. 抓取

基于自研 Fetch 平台完成视频抓取与转存，整体链路为：

**可用 URL → 本地视频 → DataSeek TOS 链接**

平台负责解析可用 URL、下载视频到本地，并将视频转存为可访问的 TOS 链接，为后续数据构造提供统一的视频输入。

### 3. 数据构造

数据构造是项目的核心环节。项目参考阿里 ReWatch-R1 公开的技术方案，生成三类带时间戳的视频训练数据：

- Video Caption
- Video QA
- Video-grounded CoT

#### 3.1 Caption 合成

##### 3.1.1 低帧率语义切段

语义分段模型 \(M_{seg}\) 以低帧率浏览完整视频，将视频切分为 \(K\) 个语义事件对应的完整时间区间：

\[
S_i=[t_{start,i},t_{end,i}]
\]

切分依据是“语义连贯、事件完整”，而非固定时长，从而尽可能保证每个片段对应一个相对完整的事件单元。

##### 3.1.2 高帧率局部描述

描述模型 \(M_{cap}\) 以高帧率逐段浏览 \(S_i\)，在每个片段内部识别多个细粒度事件 \(C_{ij}\)，并为每个事件输出相对于当前片段起点的时间戳 \(T_{ij}\)。

**分层处理的目的**：全局阶段负责识别事件边界，局部阶段将视觉注意力集中到较短片段中，从而更充分地保留动作细节、物体状态、人物交互及事件先后关系。

##### 3.1.3 时间戳重对齐

将局部事件的相对时间戳转换为全视频范围内的绝对时间戳：

\[
t_{ij}=t_{start,i}+T_{ij}
\]

随后合并所有分段事件，形成细粒度事件库 **\(C_{detail}(V)\)**。

最终生成的 Caption 本质上是一个带时间戳索引的视频事件库，用于后续 QA 生成以及 Observer 的证据检索。

#### 3.2 QA 合成

QA 合成重点解决“问题必须依赖视频细节才能作答”的问题。整体采用**对比差异生成 + 三层过滤**的方法，减少事实错误和文本捷径。

##### 3.2.1 构造信息差异

1. 由模型将细粒度事件库 \(C_{detail}(V)\) 压缩为视频摘要 \(C_{sum}\)。
2. 再由模型同时读取 \(C_{detail}(V)\) 与 \(C_{sum}\)，生成只能通过 \(C_{detail}(V)\) 回答、但无法通过 \(C_{sum}\) 回答的原始 QA。
3. 将 QA 生成任务扩展为 10 类题型，避免问题类型和推理模式过于单一。

**注意**：\(C_{sum}\) 是负信息参照，代表仅浏览视频梗概时能够获得的信息。因此，问题必须落在 \(C_{detail}(V)\) 与 \(C_{sum}\) 的信息差异上，才能真正制造对细粒度视频内容的依赖。

##### 3.2.2 三层过滤

1. **答案核验**

   输入 \(Q+C_{detail}(V)\)，验证模型生成的答案是否与构造答案 \(A\) 一致，用于筛除回答错误或缺少事实依据的样本。

   - 合格：进入下一层
   - 不合格：舍弃

2. **文本偏置核验**

   仅输入问题 \(Q\)，验证模型生成的答案是否与构造答案 \(A\) 一致，用于筛除依靠常识、语言先验或题面信息即可作答的问题。

   - 一致：说明存在文本捷径，舍弃
   - 不一致：进入下一层

3. **摘要偏置核验**

   输入 \(Q+C_{sum}\)，验证模型生成的答案是否与构造答案 \(A\) 一致，用于筛除仅凭视频梗概即可回答的简单问题。

   - 一致：说明问题对视频细节依赖不足，舍弃
   - 不一致：保留

#### 3.3 CoT 合成

CoT 合成采用多 Agent 协作模式，整体流程为：

**Reasoner 下发检索指令 → Observer 检索并汇报证据 → Reasoner 继续判断或作答 → Convert 整理并记录完整轨迹**

##### 3.3.1 定义两个 Agent

**Reasoner \(A_R\)**：负责生成思考过程 Thought 和检索动作 Action。

**Observer \(A_O\)**：负责在 \(C_{detail}(V)\) 上执行 Action，并返回观察结果 Observation。

对于给定问题 \(Q\)，两个 Agent 按以下方式循环交互：

- Reasoner 是动作的决策者和发起者。它结合问题与历史轨迹判断当前缺少的证据，生成 Thought，并提出 `segment_retrieval()` 或 `segment_query()` 等检索动作。
- Observer 是动作的执行者。它接收 Reasoner 提出的 Action，在 \(C_{detail}(V)\) 中检索相关信息，并返回 Observation。
- Reasoner 消费 Observation 并判断证据是否充分：
  - 若证据不足，则继续提出新的 Action；
  - 若证据充分，则生成 Final Answer。

##### 3.3.2 定义一个 LLM

**Convert**：在 Agent 交互结束并生成 Final Answer 后，将完整交互轨迹整理为自然语言 CoT，并使用 `<action>` 和 `<observation>` 标签显式记录检索动作与观察结果。

通过这一过程，训练数据不仅包含最终答案，还保留“判断缺少什么证据—主动检索—读取证据—继续推理”的完整链路。

### 4. 数据交付

最终交付 Caption、视频 QA 和 video-grounded CoT 三类递进式训练数据，并保留视频链接、时间戳、问题、答案、检索动作、观察结果和完整推理轨迹等关键字段，以支持后续 SFT、RLVR 训练、质量评估及 badcase 回溯。

## 项目结果

项目基于 **512 个视频**构建了三类递进式训练数据，包括：

- Caption：**512 条**
- 高难度视频 QA：**7,961 条**
- Video-grounded CoT：**6,306 条**

其中，每条 CoT 平均包含 **2.3 个推理步骤、332.5 tokens**。

基于上述数据对 inner-model-7B 进行 SFT 后，模型在 5 个视频推理 Benchmark 上的平均准确率达到 **33.25%**，较未经 SFT 的 inner-model-7B 提升 **3.51 个百分点**，验证了合成数据的有效性。

进一步引入 RL 和 O&R Reward 后，模型在 5 个视频推理 Benchmark 上的平均准确率提升至 **35.51%**，相较基础 Thinking 模型的 **27.54%** 提升 **7.97 个百分点**；同时，模型在 4 个视频理解 Benchmark 上达到 **54.15%**，较基础 Thinking 模型提升 **4.62 个百分点**。

## 项目思考

### 1. Pipeline 的整体设计合理，且具备较强的工程可维护性

整体来看，这套数据构造 Pipeline 没有让单一模型直接从长视频一步生成 QA 和 CoT，而是将流程拆分为 **Caption → QA → CoT** 三个阶段。

首先，将长视频转换为带时间戳的细粒度事件库；其次，通过 \(C_{detail}\) 与 Summary 之间的信息差，生成必须依赖视频细节才能回答的问题；最后，通过 Reasoner–Observer 循环显式检索证据并完成推理。

这种分层设计降低了模型一次性理解长视频的难度，也使每个阶段都可以独立替换模型、设置质量规则并定位错误，因此具有较强的工程可维护性和扩展性。

### 2. Pipeline 的核心价值在于提高视频依赖性与推理可追溯性

从有效性看，这套 Pipeline 最有价值的地方并不是单纯扩大数据规模，而是有意识地提高训练数据的**视频依赖性**和**推理可追溯性**。

QA 的对比差异生成机制减少了仅凭常识、语言先验或视频摘要即可作答的问题；CoT 中显式记录的 `<action>` 和 `<observation>`，则让模型学习“先定位证据，再基于证据推理并回答”，而不是直接生成一段表面合理但缺少事实支撑的思维过程。

SFT、RL 及消融实验结果证明了这条技术路线的有效性。但需要注意的是，最终效果提升同时来自合成数据、训练策略和 O&R Reward，不能将全部收益归因于某一个数据生成阶段。

### 3. 最大风险是误差级联与自验证闭环

从数据质量角度看，这套 Pipeline 最大的问题是存在明显的误差级联和闭环偏差。

\(C_{detail}\) 同时承担三种角色：

- QA 生成的事实来源；
- Observer 的检索知识库；
- Observation Reward 的核验依据。

如果 Caption 阶段遗漏了关键事件、时间戳发生偏移，或者生成了视频中不存在的细节，后续 QA、CoT 和 Reward 就可能围绕同一个错误事实形成自洽闭环。最终数据在文本层面逻辑完整，但与原始视频并不一致。

升级模型可以改善生成质量，但无法从机制上消除这一问题。同时，多层 LLM 过滤更擅长发现显性错误，却不一定能够识别细粒度视觉误判、因果关系倒置，以及“轨迹看似完整但证据实际不足”等问题。

### 4. 复现重点应从数据规模转向阶段化质量控制

因此，复现后的重点不应只是追求最终生成的数据量，而应为各阶段建立独立、可量化的质量指标。

- **Caption 阶段**：统计事件召回率、事实准确率和时间戳误差。
- **QA 阶段**：统计可回答率、视频依赖率、答案唯一性及各层过滤通过率。
- **CoT 阶段**：统计 Action 有效率、Observation 与原视频的一致性、无效检索比例，以及最终答案是否能够被已有 Observation 充分支撑。

同时，应保留一批经过人工审核的 Golden Set，并引入独立视觉模型或人工抽检，对 Caption 和 Observation 进行交叉验证，避免所有生成与质检环节都依赖同一份文本事实源。

### 5. 总体判断

总体来看，这是一套**结构合理、训练目标明确、工程上可复现**的视频数据构造 Pipeline。

但它更擅长生成“结构完整的数据”，并不天然等同于生成“事实可靠的数据”。后续优化的重点不应只是继续增加 Agent 或模型数量，而应着力切断 Caption—QA—CoT—Reward 之间的自验证闭环。

通过引入独立视觉复核、分阶段质量门槛、Golden Set 评测和 badcase 回流机制，才能真正控制最终训练数据的事实质量，并持续提升数据对视频理解和复杂推理训练的实际价值。
