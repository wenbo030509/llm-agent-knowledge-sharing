## 一、项目概览

### 背景

上游业务与算法团队计划构建新的 Pretrain Eval Set，用于补充长尾知识与 Reasoning 相关数据。原始数据来自学科竞赛题和 RL 训练集抽取，经过合成、压缩及众包修改后，存在格式错误、推理链缺失、答案与推理不一致、学科标签错误等质量问题，需要在交付前完成统一质检、修复和数据整理。

### 我的角色

负责 CoT Compressed 数据的质量保证与交付，独立设计并搭建端到端 Quality Gate Pipeline：

```text
原始/众包数据
→ 格式验证
→ 内容验证
→ Pipeline 修复
→ 学科标签纠错
→ 黑盒数据验证
→ 合格数据交付
```

职责边界：

- 我负责定义和执行数据质量标准、修复可修复样本、纠正学科标签、校验黑盒配比，并交付合格数据。
- 上游业务与算法团队负责评测目标定义、题目最终选择、评测集验证、模型运行和结果分析。
- 因此，本项目结果以数据交付质量为主，不将下游模型评测、题目区分度或最终使用效果表述为我的直接产出。

```text

            ↓
[Quality Gate Pipeline] ←── 我负责设计与执行

    │   输出：合格 / 简单废弃
    │
    ├── Gate 2：内容验证

    │

    │   输出：修复成功 → 合格 / 修复失败 → 废弃
    │

    │   ├── Step 1：硬规则匹配（query 关键词）
    │   ├── Step 2：LLM 推理生成
    │   └── Step 3：算法标签 vs 我的标签
    │       一致 → 通过 / 不一致 → 人工审判
    │
    └── Gate 5：黑盒数据验证
        输出：各学科黑盒占比约 20%
            │
            ↓
[交付上游业务与算法团队] ←── 我的职责边界到此为止
    └── 4,346 条合格数据
            │
            ↓

```

这套流程的核心不是把所有问题都交给 LLM，而是让不同节点处理不同类型的问题：

```text
确定性问题 → 规则验证
语义质量问题 → 内容验证
可修复问题 → LLM Repair
标签歧义 → 规则 + LLM + 人工审判
批次配比问题 → 统计验证
```

## 三、Gate Pipeline 技术拆解

### 3.1 Gate 1：格式验证

目标：拦截不需要语义判断的确定性错误，避免无效数据继续消耗后续处理资源。

检查内容：

```text
├── 必填字段是否存在
├── 字段类型是否正确
├── Question / CoT / Answer 结构是否完整
├── 是否存在空值、乱码或异常转义
├── 输出格式是否符合交付 Schema
└── 是否混入不允许的标记或无关内容
```

输出：

```text
格式合格 → 进入 Gate 2
简单且明确的格式坏数据 → 废弃
```

这一层适合使用代码规则，因为判断确定、成本低、结果可复现，不需要调用 LLM。

### 3.2 Gate 2：内容验证

目标：判断压缩后的 CoT 是否仍然正确、完整，并且能够支持最终答案。

核心检查：

```text
1. Question 是否完整且可回答
2. CoT 是否保留解题所需的关键推理步骤
3. 推理步骤之间是否存在逻辑断裂
4. CoT 中的计算、公式和事实是否正确
5. CoT 推导出的结论是否与 Answer 一致
6. 是否存在无关扩写、重复或明显幻觉
```

输出：

```text
内容合格 → 进入 Gate 4
内容不合格但有修复价值 → 进入 Gate 3
```

Gate 2 是整个 Pipeline 的核心质量判断。CoT Compressed 的要求不是“越短越好”，而是在压缩冗余内容后仍保留完成推理所需的最小充分信息。

### 3.3 Gate 3：Pipeline 修复（LLM Repair）

目标：修复 Gate 2 识别出的可修复内容问题，提高原始数据的有效利用率。

适合修复的问题：

```text
├── 缺少中间推理步骤
├── 推理表达不清晰
├── Answer 与正确推理结果不一致
├── 压缩后关键条件被误删
└── 存在局部冗余但主体解法正确
```

不适合修复的问题：

```text
├── Question 本身错误或条件不足
├── 原始解法方向完全错误
├── 无法确定唯一正确答案
└── 缺少足够信息判断如何修复
```

处理结果：

```text
修复成功且满足内容标准 → 合格
修复失败或无法确认正确性 → 废弃
```

LLM Repair 不是无条件重写。它只处理有明确修复边界的样本，并由 Pipeline 对修复结果进行结构与内容检查；无法确认的样本不进入交付。

### 3.4 Gate 4：学科标签纠错

目标：纠正学科标签错误，保证交付数据的学科统计和后续使用不被错误标签干扰。

完整流程：

```text
Step 1：硬规则匹配
├── 从 query 中提取高置信度学科关键词
├── 处理归属明确的样本
└── 例：“求导数” → Math，“牛顿第二定律” → Physics

Step 2：LLM 推理生成
├── 处理规则未覆盖或存在跨学科语义的样本
├── 根据题目考查的主要知识和求解方法生成学科标签
└── 产出 Pipeline 侧标签

Step 3：标签比较与人工审判
├── 算法原标签 = Pipeline 侧标签 → 通过
└── 算法原标签 ≠ Pipeline 侧标签 → 人工审判
```

设计原则：

```text
规则处理确定样本
→ LLM 覆盖模糊样本
→ 人工只处理标签分歧
```

这样既减少全量人工判断成本，也避免让 LLM 单独决定最终标签。

### 3.5 Gate 5：黑盒数据验证

目标：在合格数据中校验各学科黑盒数据占比是否符合约 20% 的项目要求。

检查方式：

```text
按学科统计：
黑盒占比 = 该学科黑盒数量 / 该学科合格数量
```

实际结果：

```text
Math       19.99%
Physics    20.09%
Chemistry  20.28%
Biology    20.12%
Other      25.00%（样本仅 12 条，基数较小）
Overall    20.06%
```

需要注意：

- 20% 是项目的数据规格，不表述为我个人制定的评测策略。
- Gate 5 是批次级统计验证，不是单条内容质检。
- `Other` 样本量很小，单条变化就会造成较大比例波动，应结合绝对数量解释。

### 3.6 Gate 之间的关系

五个 Gate 不是五个同类评分器，而是五个职责不同的处理节点：

| Gate | 处理粒度 | 判断方式 | 主要输出 |
|------|----------|----------|----------|
| Gate 1 格式验证 | 单条 | 确定性规则 | 合格 / 废弃 |
| Gate 2 内容验证 | 单条 | 内容规则与语义判断 | 合格 / 进入修复 |
| Gate 3 Pipeline 修复 | 单条 | LLM Repair + 结果检查 | 合格 / 废弃 |
| Gate 4 标签纠错 | 单条 | 规则 + LLM + 人工审判 | 最终学科标签 |
| Gate 5 黑盒验证 | 批次 | 分组统计 | 各学科黑盒占比 |

因此更准确的表述是：

> 我设计了一条由格式校验、内容质检、自动修复、标签纠错和批次配比验证组成的级联数据质量 Pipeline。

而不是：

> 我设计了五个评测指标或五个 LLM Judge。

## 四、数据状态与流转

### 4.1 数据状态

```text
RAW
→ FORMAT_PASSED
→ CONTENT_PASSED
→ REPAIR_REQUIRED
→ REPAIR_PASSED
→ LABEL_CONFIRMED
→ BLACKBOX_VALIDATED
→ DELIVERED
```

终止状态：

```text
DISCARDED_FORMAT
DISCARDED_REPAIR_FAILED
DISCARDED_UNRECOVERABLE
```

人工介入状态：

```text
LABEL_ADJUDICATION_REQUIRED
```

### 4.2 流转原则

- 每条数据保留唯一 ID，能够追踪来源、处理节点和最终状态。
- Gate 1 的确定性错误直接终止，避免浪费 LLM 和人工成本。
- Gate 2 只把有修复价值的样本送入 Gate 3。
- Gate 3 修复失败不阻塞整批任务。
- Gate 4 仅把标签分歧样本交给人工审判。
- Gate 5 在单条数据处理完成后进行批次级校验。

### 4.3 建议保留的日志字段

```text
sample_id
source
original_subject
pipeline_subject
final_subject
format_check_result
content_check_result
repair_status
repair_reason
label_match
adjudication_result
is_blackbox
final_status
pipeline_version
```

这些字段支持定位某类错误主要出现在哪个来源、哪个 Gate，以及规则升级后哪些历史数据需要重新处理。

## 五、CoT Compressed 的质量标准

### 5.1 压缩目标

```text
压缩前：完整但可能冗长、重复、包含无关解释
压缩后：保留完成推理所需的关键条件、步骤和结论
```

压缩不是摘要，也不是只保留最终答案。合格 CoT 至少满足：

1. 关键已知条件仍然存在。
2. 关键公式或推理规则没有被删掉。
3. 中间结论能连接前一步和后一步。
4. 最终答案能够由保留的推理过程推出。
5. 没有与正确解法冲突的内容。

### 5.2 两类典型风险

**压缩不足：**

```text
问题：重复、冗长、token 成本高
处理：删除无关解释和重复推导
```

**压缩过度：**

```text
问题：关键步骤丢失，形成逻辑跳跃
处理：补回必要中间过程；无法可靠补回则废弃
```

### 5.3 可学习性的准确表述

本项目可以从数据质量角度检查 CoT 是否具备完整、正确和清晰的推理信号，但不直接声称已经通过模型实验验证其 Learnability。

准确说法：

> 我负责保证压缩后的 CoT 在数据层面保留最小充分推理链；这些数据是否能提升模型能力，由上游业务与算法团队在实际评测中验证。

## 十、面试官追问准备

### Q1：为什么设计成级联 Pipeline，而不是一个 LLM 全量判断？

格式和字段问题可以由确定性规则稳定处理，没有必要消耗 LLM。内容修复需要生成能力，才交给 LLM；学科标签存在歧义时，再通过规则、LLM 和人工审判组合解决。级联设计同时降低成本、减少不确定性，并能明确每条数据在哪个节点失败。

### Q2：Gate 2 的“内容合格”怎么定义？

主要看四点：CoT 是否保留必要条件和关键推理步骤，推理过程是否正确，步骤之间是否连贯，以及最终 Answer 是否能由 CoT 推出。不是越长越好，也不是答案正确就算合格。

### Q3：LLM Repair 会不会引入新错误？

会，所以只修复边界明确、主体解法仍然成立的样本。Pipeline 会检查修复结果是否满足结构和内容标准；无法确认正确性或修复失败的样本直接废弃，不为了提高合格率强行保留。

### Q4：为什么标签纠错要同时用规则、LLM 和人工？

高置信度关键词适合规则，成本低且稳定；规则覆盖不到的跨学科或语义模糊题交给 LLM；算法原标签与 Pipeline 标签不一致时再人工审判。这样人工只处理真正有分歧的少量样本。

### Q5：黑盒 20% 是你制定的吗？

不是，这是项目的数据规格。我的职责是按学科统计并验证交付数据是否满足该要求。实际整体占比是 20.06%，数学、物理、化学和生物都接近 20%。

### Q6：79.06% 合格率是高还是低？

它首先是一个真实交付结果：5,497 条输入中有 4,346 条满足质量标准。单看比例无法判断高低，还要结合原始数据质量、修复成本和废弃原因。更重要的是不能为了提高合格率放宽内容正确性。

### Q7：如何证明你的 Pipeline 有效？

在我的职责范围内，可以检查各 Gate 的错误拦截、修复结果抽检、标签分歧仲裁和最终交付统计。模型评测和评测集效果属于下游验证，应由上游业务与算法团队提供结果，不能用推测代替。

### Q8：这个项目和评测集有什么关系？

我参与的是评测集数据建设中的质量保障和交付环节，确保候选数据在格式、内容、标签和黑盒配比上满足要求。我不负责评测方案设计、模型跑分和结果分析，这些由上游业务与算法团队完成。

### Q9：如果数据量扩大十倍，瓶颈在哪里？

Gate 1 的规则校验可以线性扩展；主要瓶颈会出现在 Gate 2/3 的语义判断和 LLM Repair，以及 Gate 4 的人工审判。优化方向包括批处理、并发、失败重试、规则前置和降低人工分歧率。

### Q10：如果重新做一次，最优先补什么？

优先补齐每个 Gate 的失败原因统计和 Pipeline 版本管理。这样可以知道主要损耗来自格式、内容、修复失败还是标签分歧，也能保证规则变化后不同批次的交付口径可比较。

## 十一、典型 Badcase

### BC-01：格式不合规

```text
现象：缺失 Answer 字段、混入异常 Markdown、编码乱码
归属：Gate 1
处理：简单废弃
```

### BC-02：CoT 推理链断裂

```text
现象：从已知条件直接跳到结论，缺少必要中间步骤
归属：Gate 2 → Gate 3
处理：可可靠补全则修复，否则废弃
```

### BC-03：Answer 与 Reasoning 不一致

```text
现象：推理得到 x=5，Answer 写成 x=6
归属：Gate 2 → Gate 3
处理：能根据正确推理明确修正则修复，否则废弃
```

### BC-04：原始题目不可修复

```text
现象：题目条件不足、答案不唯一或主体解法完全错误
归属：Gate 3
处理：修复失败，废弃
```

### BC-05：学科标签冲突

```text
现象：跨学科题被硬规则和算法标签判为不同学科
归属：Gate 4
处理：人工审判，确定最终标签
```

### BC-06：黑盒配比偏差

```text
现象：某学科黑盒数量与约 20% 的项目要求不一致
归属：Gate 5
处理：记录并反馈批次配比问题
```
